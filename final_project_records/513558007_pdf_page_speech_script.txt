題目：使用 AFL++ 對 Fuzzgoat 進行自動化模糊測試與漏洞分析
學生：513558007 黃昭彬

第 1 頁：封面
各位老師、同學大家好，我是 513558007 黃昭彬。今天我要報告的期末專案題目是「使用 AFL++ 對 Fuzzgoat 進行自動化模糊測試與漏洞分析」。這個專案主要結合軟體測試與程式安全，透過 AFL++ 自動產生測試輸入，再使用 AddressSanitizer 進行 crash replay 和 root cause analysis。我的重點不是只展示有多少 crash，而是把這些 crash samples 轉換成可以重現、可以分類、也可以追溯到原始碼位置的分析結果。

第 2 頁：專案背景與方法
這一頁先介紹專案背景。AFL++ 是一個常見的 coverage-guided fuzzer，也就是它會根據程式執行覆蓋率來引導輸入變異。測試目標 Fuzzgoat 則是一個故意放入多個記憶體安全問題的開源靶機，適合用來練習 fuzzing 和漏洞分析。這次我的分析範圍，是 GitHub repository 裡 out/default/crashes/ 目錄下全部 65 個 AFL++ crash samples。原本我以為樣本數是 63 個，但重新檢查 GitHub 後確認是 65 個，所以 final report 採用完整分析，不排除任何樣本。

第 3 頁：專案摘要
這頁說明整體研究流程。我先使用 AddressSanitizer 版本的 fuzzgoat_ASAN，對 65 個 crash samples 逐一回放，確認每個輸入是否能重現 crash。接著，我分析 AddressSanitizer 輸出的錯誤類型與 stack trace。因為部分 stack trace 一開始只有 binary offset，沒有完整原始碼行號，所以我再使用 addr2line，把偏移位址轉換成 main.c 或 fuzzgoat.c 的具體行號。最後，我將 65 個 crash 歸納成 5 個主要 stack groups，並針對代表樣本做 root cause analysis。

第 4 頁：GitHub 活動與提交紀錄
這頁是 GitHub 活動紀錄。我的 repository 是 2205jg/513558007-Fuzzing-Study，主要 branch 是 master。專案中與我相關的提交有兩個。第一個是 003e4b3，主要更新 README，記錄 AFL++ 和 AddressSanitizer 的建置與除錯進度。第二個是 c3da5bf，這個提交上傳了 65 個 AFL++ crash samples，以及 fuzzgoat_ASAN 測試用二進位檔。這些提交讓整個實驗不只是截圖，而是可以透過 GitHub 保存並重現的測試紀錄。

第 5 頁：系統化測試與分析方法
這頁是實作方法。第一步，我把專案 clone 到 WSL/Linux 的原生檔案系統，因為 AFL++ 產生的 crash 檔名包含冒號，例如 sig:06、time:...，這種檔名在 Windows 會造成 checkout 失敗。第二步，我用 fuzzgoat_ASAN 對 65 個 crash payload 逐一回放，記錄 AddressSanitizer 類型、退出狀態與 AFL++ signal。第三步，我用 addr2line 做符號化還原，把 AddressSanitizer 裡的記憶體偏移量對應回 Fuzzgoat 原始碼的具體行號。透過這三步，才能把 crash 轉成可分析的漏洞證據。

第 6 頁：模糊測試核心數據指標
這頁是核心數據。這次總共分析 65 個 crash samples。從結果來看，絕大多數 crash 都跟 heap memory 有關，顯示 Fuzzgoat 在動態記憶體生命週期管理上存在明顯問題。AFL++ signal 的分布也很重要：sig:06 有 30 例，通常代表 AddressSanitizer 偵測到錯誤後 abort；sig:11 有 35 例，通常是 segmentation fault。雖然樣本有 65 個，但它們不是 65 個完全不同的漏洞，而是高度重複地觸發少數幾條 vulnerable paths。

第 7 頁：漏洞類型佔比分佈
這頁可以看出主要漏洞類型分佈。數據顯示，heap-buffer-overflow 是最多的一類，佔比大約六成。這代表許多輸入最後都觸發了 heap buffer 邊界外讀取或寫入。這跟 Fuzzgoat 中對字串與 JSON buffer 的不安全處理有關。簡單說，fuzzing 產生了很多不同 payload，但這些 payload 常常會收斂到同一個危險位置，所以看比例時，我們看的不是檔案數量而已，而是它們背後對應的程式碼問題。

第 8 頁：漏洞統計與核心堆棧分析
這頁是最重要的分類表。65 個樣本分成四類。第一類 heap-buffer-overflow 有 39 個，主要位置是 main.c:150 和 fuzzgoat.c:258。第二類 heap-use-after-free 有 16 個，主要位置是 fuzzgoat.c:643，也就是 json_parse_ex。第三類 invalid-free / bad-free 有 9 個，主要位置是 fuzzgoat.c:85，也就是 default_free。最後 segmentation-fault 有 1 個，主要位置是 fuzzgoat.c:224，也就是 json_value_free。這個表說明我不是只看 AddressSanitizer 類型，也有把 source location 一起納入分類。

第 9 頁：代表性漏洞根因分析（一）
這頁介紹前兩個代表樣本。第一個是 id:000000，類型是 invalid-free / bad-free。它的根因是程式進入資源釋放流程時，呼叫 default_free，但傳入的位址不是 malloc 建立的 heap 起始位址，所以 AddressSanitizer 報出 attempting free on address which was not malloc()-ed。第二個是 id:000003，類型是 heap-buffer-overflow。它的問題在 main.c，程式只配置 file_size 大小的 buffer，卻直接用 printf("%s") 當成 C 字串輸出，沒有補上 NUL 結尾，因此 printf 會讀超過 buffer 邊界。

第 10 頁：代表性漏洞根因分析（二）
這頁補充另外三個 stack groups。id:000014 是 heap-use-after-free，主要位置在 fuzzgoat.c:643。它的原因是 Fuzzgoat 中有特意放入的 free(*top) 漏洞路徑，物件被釋放後，後續解析流程仍然使用該指標。id:000016 是另一種 heap-buffer-overflow，位置在 fuzzgoat.c:258，原因是 value->u.object.length-- 先取值再遞減，造成 object values 越界存取。id:000027 是唯一的 segmentation-fault，位置在 fuzzgoat.c:224，推測是前面多重記憶體錯誤破壞了釋放流程中的狀態，最後在 json_value_free 發生段錯誤。

第 11 頁：實作挑戰與解決方案
這頁說明我在實作上遇到的問題。第一個挑戰是 Windows 無法正確簽出 AFL++ crash 檔名，所以我改用 WSL2/Linux 原生檔案系統。第二個挑戰是 AddressSanitizer 輸出缺少 source symbol，所以我用 addr2line 手動轉換 offset。第三個挑戰是樣本數和預期不同，最後確認 GitHub 上是 65 個，因此全部保留並回放。第四個挑戰是 crash 重複度高，所以我沒有逐一寫 65 段，而是用 AddressSanitizer 類型和原始碼位置進行分群，整理成 4 大漏洞行為與 5 大 stack groups。

第 12 頁：專案結論與未來方向
最後總結。本專案完成了從 AFL++ fuzzing、crash corpus 保存、AddressSanitizer replay，到 root cause analysis 的完整流程。最重要的成果是確認 GitHub 上 65 個 crash corpus 都可以作為可重現的漏洞證據，並成功分析代表樣本的根因。未來如果要延伸，可以使用 afl-tmin 對代表 payload 做最小化，去掉不必要的 mutated padding。接著可以修補 main.c:150、fuzzgoat.c:258 和 fuzzgoat.c:643 等問題，再用原本的 crash corpus 做 regression testing，確認漏洞是否真正被修好。我的報告到這裡，謝謝大家。
