各位老師、同學大家好，我是 513558007。

我這次期末專案的題目是：使用 AFL++ 對 Fuzzgoat 進行模糊測試與漏洞分析。

Fuzzgoat 是一個故意放入多個記憶體安全問題的 C 語言程式，常用來測試 fuzzer 或安全分析工具的效果。我的目標不是只跑出 crash，而是建立一個可以重現、可以追蹤、也可以分析根因的測試流程。

這次 final report 的重點，是針對 GitHub 上已經上傳的 crash samples 做完整分析。我原本以為有 63 個樣本，但重新檢查 repository 後，實際上 out/default/crashes/ 裡有 65 個 AFL++ crash samples，所以我最後是分析全部 65 個樣本，沒有排除任何樣本，包括之前已經看過的 id:000000 和 id:000003。


接下來說明我的分析流程。

第一步，我把 GitHub repository clone 到 WSL/Linux 環境。這一步很重要，因為 AFL++ 產生的 crash 檔名裡面有冒號，例如 sig:06、time:...，這種檔名在 Linux 可以存在，但在 Windows 上 checkout 會失敗。

第二步，我用 AddressSanitizer 版本的 fuzzgoat_ASAN 逐一回放每個 crash sample。也就是對每個 id:* 檔案執行：

fuzzgoat_ASAN <sample>

第三步，我記錄每個樣本的 AddressSanitizer 錯誤類型、signal、payload size、exit code、SHA-256，以及 stack trace。

第四步，因為 AddressSanitizer 輸出一開始沒有完整顯示 source line，所以我再用 addr2line 把 binary offset 對應回原始碼位置，例如 main.c:150 或 fuzzgoat.c:85。

最後，我不是逐一寫 65 段重複說明，而是依照錯誤類型和 source-level stack location 做分類，並挑代表樣本做根因分析。


這次總共分析 65 個 crash samples。

分類結果如下：

第一類是 heap-buffer-overflow，共有 39 個樣本，是數量最多的一類。

第二類是 heap-use-after-free，共有 16 個樣本。

第三類是 invalid-free / bad-free，共有 9 個樣本。

最後還有 1 個樣本是 segmentation-fault。

從 AFL++ 的 signal 來看，sig:06 有 30 個，sig:11 有 35 個。

雖然看起來有 65 個 crash samples，但實際分析後發現，它們不是 65 個完全不同的漏洞，而是很多 mutated inputs 重複觸發少數幾條 vulnerable paths。最後可以整理成 4 類漏洞，以及 5 個主要 stack groups。


接著我說明幾個代表樣本。

第一個代表樣本是 id:000000。

這個樣本的 AddressSanitizer 類型是 attempting free on address which was not malloc()-ed，我把它分類為 invalid-free / bad-free。

透過 addr2line 對應後，主要位置是在 default_free at fuzzgoat.c:85。這表示程式呼叫 free() 時，傳入的指標不是合法的 malloc 起始位址，所以 AddressSanitizer 偵測到不合法釋放。

這類問題的危險在於，如果程式嘗試釋放錯誤位址，可能造成 heap metadata 被破壞，進一步導致 crash 或潛在利用風險。


第二個代表樣本是 id:000003。

這個樣本屬於 heap-buffer-overflow，主要位置在 main.c:150，另外可以看到配置位置大約在 main.c:129。

根因是 main.c 中配置檔案內容時，只配置了 file_size 大小的 buffer，接著卻用 %s 把它當成 C 字串輸出。

C 字串需要以 NUL 結尾，但這裡沒有多配置一個 byte，也沒有手動補上 NUL。所以當 printf("%s\n", file_contents) 執行時，就可能一路讀超過配置範圍，造成 heap-buffer-overflow。

這也是為什麼很多樣本都集中在 main.c:150，因為不同的輸入都可能觸發同一個輸出路徑。


第三個代表樣本是 id:000014。

這個樣本是 heap-use-after-free，主要位置在 json_parse_ex at fuzzgoat.c:643，同時也可以追到 json_parse 和 main.c:156。

根因跟 Fuzzgoat 裡故意加入的漏洞有關。程式在某些 JSON array 處理路徑中，會先呼叫 free(*top)，但後續流程仍然可能使用到被釋放的 heap 物件。

這就是典型的 use-after-free：記憶體已經被釋放，但程式仍然保留指標並繼續讀取或操作它。

這類問題在真實軟體中很嚴重，因為如果攻擊者可以控制 heap 配置狀態，就可能造成更進一步的利用。


第四個代表樣本是 id:000016。

它也是 heap-buffer-overflow，但跟剛剛 main.c:150 那一群不同。這個樣本主要位置在 json_value_free at fuzzgoat.c:258。

這裡的問題是 object free path 使用了：

value->u.object.length--

也就是先使用原本的 length，再遞減。正確邏輯通常應該是先遞減再取值，也就是：

--value->u.object.length

因為這個順序錯誤，程式會讀到 object values 邊界外的位置，造成越界存取。這說明同樣是 heap-buffer-overflow，也可能來自不同的根因，所以分類時不能只看 AddressSanitizer 類型，也要看 source location。


第五個代表樣本是 id:000027。

這個樣本是唯一的 segmentation-fault。它主要定位在 json_value_free at fuzzgoat.c:224，並且後續在 main.c:166 的釋放流程中崩潰。

這個 case 顯示程式在釋放 JSON value 結構時，內部狀態可能已經被前面的錯誤破壞。最後程式嘗試讀取不合法位置，因此觸發 SEGV。

我把它獨立分類，是因為它不是 AddressSanitizer 明確標成 use-after-free 或 buffer-overflow，而是以 deadly signal 的形式出現。


這次專案中也解決了幾個實作上的問題。

第一個問題是 Windows 無法處理 AFL++ crash 檔名。解法是改到 WSL/Linux 環境中 clone repository 和 replay samples。

第二個問題是 AddressSanitizer stack trace 沒有完整 source line。解法是使用 addr2line，把 fuzzgoat_ASAN 的 binary offset 轉回 main.c 和 fuzzgoat.c 的行號。

第三個問題是樣本數一開始和預期不同。原本以為是 63 個，但重新統計 Git tree 後確認是 65 個，所以 final report 改成分析全部 65 個。

第四個問題是很多 crash samples 看起來不同，但其實觸發同一路徑。解法是依照 AddressSanitizer 類型和 source location 分群，而不是把每個樣本都當成獨立漏洞。


最後總結。

這次專案完成了從 AFL++ fuzzing、crash corpus 保存、AddressSanitizer replay，到 source-level root cause analysis 的完整流程。

最重要的發現是：65 個 crash samples 可以歸納成 4 類漏洞與 5 個主要 stack groups。這也符合 fuzzing 的特性，也就是大量變異輸入常常會重複觸發少數幾個真正的 vulnerable paths。

如果後續要繼續做，我會建議三件事。

第一，使用 afl-tmin 對代表樣本做最小化，讓每個 crash input 更容易閱讀與保存。

第二，修補主要問題，例如 main.c:150 的 buffer 結尾問題、fuzzgoat.c:137 的 use-after-free 路徑，以及 fuzzgoat.c:258 的 object length 遞減錯誤。

第三，修補後再用同一批 crash corpus 做 regression test，確認問題是否真的被解決。
